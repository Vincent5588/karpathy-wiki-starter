# 經驗法則 5：promote 判斷精煉

> 跑 `wiki-status-promote` 時，兩條精煉 default 判斷的規律。來源：一次批次升 stable 的實作歸納——3 個含待解、2 個當天才建的 entity 照樣該升 stable，證明現行 default 太保守。

## 精煉 1：`## 待解` 要分兩型

skill 的 default 把「含 `## 待解 / 矛盾` 區塊」一律歸 🟡 留 draft——**太粗**。待解分兩型：

| 型 | 特徵 | 對 promote |
|---|---|---|
| **未來 / 取決於** | 「Phase N 才需要」「參數待補」「值待實測」——內容沒錯，只是還沒展開 | ✅ **不擋 stable**（保留待解區塊即可）|
| **矛盾 / 存疑** | 「與 X 衝突」「此處可能錯」「兩說不一」——內容本身待裁決 | 🟡 **強制留 draft**，直到裁決 |

→ 判斷時讀待解的**內容**，不是只看「有沒有 `## 待解`」。

## 精煉 2：同 session owner 逐輪共審 → 可直接升 stable

- 這是 `status` 鐵則「**stable = trust marker，不是 mtime**」的延伸：entity 雖然是當天 `created`，但**若 owner 在本 session 逐輪審過**（改錯、加內容、定結構）＝ 人類審查已經成立 → **不必等 30 天**即可升 stable。
- 反面同樣成立：LLM 自建但 owner **沒**過目的 entity，放 30 天也**不該**自動升——trust 未建立，**age 不等於 trust**。

## 精煉 3：待解要看「未解的東西是不是這頁立論的承重點」

精煉 1 分「未來型 vs 矛盾型」還不夠——批次審查中常出現「待解裡有『衝突／對不上／未查證』字樣，但根本不擋」的情況。真正的判準是**承重與否**：

| 未解的東西 | 判定 | 說明 |
|---|---|---|
| **是這頁立論的前提** | 🟡 留 draft | 例如「某個機制是否真的隔離」未經查證，而整頁的結論就建立在「有隔離」這個假設上 |
| **是背景資料 / 佐證細節** | ✅ 可升 | 例如某個歷史年份或條號未逐源查證，但缺了不影響本頁主張 |
| **是對外部工具的未知**（本頁沒據此下斷言）| ✅ 可升 | 誠實標「某工具是否支援某功能尚未查證」，只要頁面沒拿它當論據，誠實劃界不是內容缺陷 |

### 三種「看起來像矛盾、其實已經解決」的形態

批次審查中最常誤判的一類——**待解區塊在描述「我怎麼處理了這個衝突」，而不是「這裡有個沒解的衝突」**：

| 形態 | 說明 |
|---|---|
| **軸線區分表** | 開頭就用對照表把「這個概念」跟「容易搞混的另一個概念」的分工講清楚 |
| **立場分層表** | 用多欄對照呈現「業界原始定義／本 vault 的權威說法／某個來源的詮釋」，衝突已經被分層化解 |
| **定名說明** | 明確寫「後人有別的說法，但本頁以某個一手來源為準」，衝突已裁決成「選邊」 |

⭐ **心法**：看待解區塊在「提問」還是在「交代已經怎麼處理」。前者擋，後者不擋。

⚠️ **常見現象**：不少 entity 會在自己的待解區塊裡就自標「已解決」或「待確認」——**前一位作者早就分過型，promote 腳本的關鍵字掃描讀不出來**。這正是本法則存在的理由：`## 待解` 的**有無**是結構訊號，**內容**才是判斷依據。

## 精煉 4：`inlinks ≥ 1` 只證明「有人提過它」，不證明「值得當知識依據」

promote 腳本用 inlinks 數當主要信號，但它看不出知識密度。

| 判準 | 說明 |
|---|---|
| **字數不是判準** | 字數不多但掛在高 inlink 主題下、屬完整概念系列一部分的頁面，照樣該升 |
| **「有沒有可獨立引用的知識」才是** | 只有「我方不選用某工具」這類單一結論、沒有可被獨立引用內容的短頁，優先考慮**合併進主體 entity**，而不是升 stable |
| 反向也成立 | inlinks 低但內容完整（例如一篇完整的人物或主題介紹頁）照樣可升——**inlinks 低有時只代表這個系列還在長**，不是內容單薄 |

→ 判定為「該合併」時，**留 draft ＋ 加 `review_by`**（未來回頭決定合併或廢棄），不要當場 deprecate。

## How to apply

跑 promote 時：

1. 對每個含待解的 candidate，讀待解型別 → 未來型照升、矛盾型留 draft。
2. 若在提問而非交代處理，再問**那個未解的東西是不是這頁立論的承重點**——承重才留 draft，背景資料／外部工具未知不擋。
3. 今天建、但 owner 本 session 審過的，列 🟢 並註明「owner 共審」。
4. 別只看 inlinks——單一結論型的短頁即使有 inlink 也該考慮合併而非升 stable，判定該合併時留 draft ＋ 加 `review_by`。
5. 仍照規則 E（show before write），owner 最終拍板。
